# CLAUDE.md — Project Knowledge Base

A working reference for building autonomous agents on **Claude Managed
Agents (MA)**, written from scratch and stress-tested through this project.
Read this before touching the code or building a new agent.

---

## What this project is

A **landing page generator agent**: input an idea, output a deployed URL.
The agent generates a complete `index.html`, deploys it via a custom tool,
iterates against a rubric until a grader signs off, and returns the URL —
fully autonomous, no human in the loop.

The architecture generalizes. Swap the rubric, system prompt, and custom
tool, and you have an agent for any "generate-then-evaluate" task.

## Mental model: the four core MA concepts

| Concept | What it is | Lifecycle |
|---|---|---|
| **Agent** | Persisted, versioned config: model + system prompt + tools + MCP servers + skills. Created with `client.beta.agents.create()`. | One-time setup. Reused across many sessions. |
| **Environment** | Template for provisioning containers (networking, packages). Created with `client.beta.environments.create()`. | One-time setup. Reused across many sessions. |
| **Session** | A stateful interaction with an agent. References a pre-created agent + environment. | Per request. New session per run. |
| **Container** | Isolated compute where the agent's *tools* execute (bash, file ops, code). The agent loop itself runs on Anthropic's orchestration layer, not in the container. | Provisioned per session, torn down on session end. |

```
Agent (config) ──────▶ Anthropic orchestration (runs the loop)
                                │ tool calls
                                ▼
Environment (template) ──▶ Container (where tools execute)
                                │
                          Session ──── event stream ◀───── your client
                                ├─ resources (files, repos)
                                ├─ vault_ids (MCP credentials)
                                └─ conversation history
```

## ⚠️ The mandatory flow — every project starts here

```
1. agents.create()      ← ONCE. Store the ID. Never call in the request path.
2. environments.create()← ONCE. Store the ID.
3. sessions.create(agent=AGENT_ID, environment_id=ENV_ID)   ← every run
```

**Why:** the agent is a versioned object. Each `agents.update()` creates a
new immutable version. Sessions pin to a version, so you can iterate the
prompt without breaking running sessions, roll back, or A/B test.

**Anti-pattern:** calling `agents.create()` at the top of every script run.
Accumulates orphans, pays create latency for nothing, defeats versioning.
In this project, `scripts/setup.py` is the agent-create boundary — never
call it from `run.py`.

**The session takes a *pointer*, not config.** `model`, `system`, `tools`,
`mcp_servers`, `skills` live on the agent object. The session only takes
`agent="agent_..."` (string shorthand → latest version) or `agent={"type":
"agent", "id": ..., "version": N}` (pinned).

## Defined Outcomes — the killer feature for autonomous agents

This is the unlock. Don't build your own eval loop.

### What it is

Send a `user.define_outcome` event to a session with:

- `description` — what to build
- `rubric` — markdown criteria the grader evaluates against
- `max_iterations` — default 3, max 20

The system spins up a **separate grader agent in its own context window**
(unbiased — doesn't see the agent's reasoning). The grader evaluates the
artifact, feeds critique back to the agent, and the agent revises. Loop
until rubric met or `max_iterations` hit.

### Wire shape

```python
client.beta.sessions.events.send(
    session_id=session.id,
    events=[{
        "type": "user.define_outcome",
        "description": "Generate and deploy a landing page for: <idea>",
        "rubric": {"type": "text", "content": rubric_markdown},
        # alternatively: {"type": "file", "file_id": uploaded.id}
        "max_iterations": 4,
    }],
)
```

### How to write a rubric

Live example: `src/rubric.md`. Patterns that worked:

- **Be explicit and binary.** "Includes `<meta name=\"viewport\" ...>` in
  `<head>`" passes/fails cleanly. "Looks good on mobile" is unscorable.
- **Group by category** with section headers (Structure / Copy quality /
  Analytics / Technical / Deployment). Graders use these as outline.
- **Forbid puffery by exact phrase.** "No filler phrases: avoid 'next-gen',
  'leverage synergies', 'game-changing'" — much more enforceable than "no
  marketing speak".
- **Tie to mechanics.** "Every CTA has `data-cta=\"<slug>\"`" gives the
  grader something concrete to grep for.
- **Include the deploy step.** "The `deploy_site` tool was successfully
  called" makes deployment part of the success criterion, not an
  afterthought.

### Beta header

`define_outcome` works under the **standard** `managed-agents-2026-04-01`
header that the SDK adds automatically. **Do NOT pass
`managed-agents-2026-04-01-research-preview`** — it 404s on both
`events.send` and `events.stream`. (Older docs sample shows it; outdated.)

## Tools — what the agent can actually do

Three kinds of tools, declared on the agent (not the session):

| Type | Where it runs | When to use |
|---|---|---|
| `agent_toolset_20260401` | Anthropic's container | Default toolkit: bash, read, write, edit, glob, grep, web_fetch, web_search. Enable all or per-tool. |
| `mcp_toolset` | Anthropic's container, via MCP server URL | Third-party integrations (GitHub, Linear, Asana). Credentials live in a **vault** (separate concept), not inline. |
| `custom` (with `input_schema`) | **Your client code** | Anything where you want host-side control: secrets you can't put in the container, deploy actions, calls into your existing systems. |

### Custom tool flow (this project's pattern)

This is the security boundary you want for anything touching real systems.

```
1. Agent generates a tool call → emits `agent.custom_tool_use` event
2. Session goes idle waiting for a result
3. Your orchestrator runs the actual logic host-side (with host's credentials)
4. Orchestrator posts back `user.custom_tool_result` with the output
5. Session resumes, agent continues
```

The Netlify token, Vercel token, GitHub PAT, etc. **never enter the agent
container** because the call happens in your orchestrator. Same model
applies to: hitting your DB, calling internal APIs, anything CLI that needs
a credential.

The wire shape:

```python
# Agent declares a custom tool at agents.create() time:
DEPLOY_TOOL = {
    "type": "custom",
    "name": "deploy_site",
    "description": "Deploys HTML and returns the public URL.",
    "input_schema": {
        "type": "object",
        "properties": {
            "html":  {"type": "string"},
            "title": {"type": "string"},
        },
        "required": ["html", "title"],
    },
}

# At runtime, when agent.custom_tool_use fires:
tool_input = event.input  # already parsed dict
result_url = run_my_tool(tool_input)

client.beta.sessions.events.send(
    session_id=session.id,
    events=[{
        "type": "user.custom_tool_result",
        "custom_tool_use_id": event.id,   # NOT event.tool_use_id
        "content": [{"type": "text", "text": f"Deployed: {result_url}"}],
        # "is_error": True  on failure
    }],
)
```

**Critical:** the field on the event is `event.name`, NOT `event.tool_name`.
Same for `event.id` (the tool_use_id), NOT `event.tool_use_id`. Burned us
once.

## Events & Streaming

### Two ways to receive events

```python
# Streaming (SSE) — primary, real-time
with client.beta.sessions.events.stream(session_id=session.id) as stream:
    for event in stream:
        ...

# Polling (paginated GET) — for history / reconnect catch-up
events = client.beta.sessions.events.list(session_id=session.id, limit=200)
```

### Event types you'll actually see

| Type | Meaning |
|---|---|
| `session.status_running` | Agent is actively working |
| `session.status_idle` | Agent paused — check `stop_reason` to know why |
| `session.status_terminated` | Session is done, no resume possible |
| `session.error` | Something went wrong; usually paired with terminate |
| `agent.message` | Text content blocks from the agent |
| `agent.thinking` | Adaptive thinking traces (usually omitted) |
| `agent.tool_use` | Built-in tool call (toolset) |
| `agent.custom_tool_use` | Custom tool call — **YOU must respond** |
| `agent.thread_context_compacted` | History was compacted automatically |
| `span.model_request_start` / `_end` | Model inference span — `_end` has token usage |
| `span.outcome_evaluation_start` / `_ongoing` / `_end` | Grader running |

### The terminal-idle gate (do not get this wrong)

`session.status_idle` is **not** a terminal state. It fires whenever the
agent pauses, including waiting for your custom-tool response. Break only
when `stop_reason.type` is something other than `requires_action`:

```python
def is_terminal_idle(event):
    if event.type != "session.status_idle":
        return False
    stop = event.stop_reason
    if stop is None: return True
    stop_type = stop.type if hasattr(stop, "type") else stop.get("type")
    return stop_type != "requires_action"
```

Other terminal stop_reasons: `end_turn`, `retries_exhausted`. Plus
`session.status_terminated` is always terminal.

### Stream-first ordering

**Open the stream BEFORE sending the kickoff event.** The stream only
delivers events that arrive after it opens. If you `events.send()` first
and then open the stream, early events get buffered and arrive in one
batch — you lose the ability to react to them in real time.

```python
# ✓ correct
with client.beta.sessions.events.stream(session_id=sid) as stream:
    client.beta.sessions.events.send(session_id=sid, events=[kickoff])
    for event in stream: ...

# ✗ wrong
client.beta.sessions.events.send(session_id=sid, events=[kickoff])
with client.beta.sessions.events.stream(session_id=sid) as stream: ...
```

### Reconnect with consolidation

The SSE stream has no replay. If the connection drops, reconnect with
`events.list()` for history, dedup by `event.id`, then resume the live
stream. Pattern:

```python
seen = set()
while True:
    try:
        with client.beta.sessions.events.stream(session_id=sid) as stream:
            # 1. Catch up via history first
            for ev in client.beta.sessions.events.list(session_id=sid).data:
                if ev.id in seen: continue
                seen.add(ev.id); handle(ev)
            # 2. Tail live stream
            for ev in stream:
                if ev.id in seen: continue
                seen.add(ev.id); handle(ev)
                if is_terminal(ev): return
    except (httpx.RemoteProtocolError, ConnectionError):
        continue  # reconnect
```

We hit `httpx.RemoteProtocolError: peer closed connection without sending
complete message body` on a long-running session. The current `run.py`
doesn't reconnect — for production, add the loop above.

### Grader runs in its own session thread (this bit you)

When defined-outcomes is active, the grader is a sub-agent with its own
thread. **The grader can issue its own tool calls** as internal probes.
Those events arrive on your stream with `session_thread_id` set to a
non-null value. You will get a 400 if you try to respond to them on the
main session.

**Skip them.** The grader resolves its own thread internally:

```python
if event.session_thread_id is not None:
    # grader-internal — leave it alone
    continue
```

This took us a full session-debug to figure out. Live in `src/run.py:152`.

## Networking config — what to give your environment

```python
env = client.beta.environments.create(
    name="my-env",
    config={
        "type": "cloud",
        "networking": {"type": "unrestricted"},  # full egress
    },
)
```

Other networking modes:
- `{"type": "unrestricted"}` — full internet, simplest
- `{"type": "limited", "allowed_hosts": ["api.example.com"]}` — package
  managers + your allowlist
- `{"type": "package_managers_and_custom", "allowed_hosts": [...]}` — same
  idea, older naming

**Gotcha:** If you use limited networking and the agent has MCP servers,
you must allow those domains too — otherwise tools silently fail.

This project uses `limited` with empty `allowed_hosts` because the agent
doesn't need any container-side internet (deploy happens via custom tool
in the orchestrator).

## Vaults & MCP (we don't use here, but FYI for future agents)

If you build an agent that talks to GitHub / Linear / Notion / etc. via
MCP, **don't put auth tokens in the agent config**. They'd be exposed in
the agent object and frozen across versions.

Instead:

1. Agent declares the MCP server (URL only, no auth):
   ```python
   mcp_servers=[{"type": "url", "name": "linear", "url": "https://mcp.linear.app/mcp"}]
   tools=[{"type": "mcp_toolset", "mcp_server_name": "linear"}]
   ```

2. Create a **vault** with the OAuth credentials:
   ```python
   vault = client.beta.vaults.create(name="linear-creds")
   client.beta.vaults.credentials.create(
       vault_id=vault.id,
       display_name="Linear OAuth",
       auth={
           "type": "mcp_oauth",
           "mcp_server_url": "https://mcp.linear.app/mcp",
           "access_token": "...",
           "expires_at": "...",
           "refresh": {"refresh_token": "...", "client_id": "...", "token_endpoint": "...", "token_endpoint_auth": {"type": "client_secret_basic", "client_secret": "..."}},
       },
   )
   ```

3. Attach the vault to the **session** (not the agent):
   ```python
   sessions.create(agent=agent.id, environment_id=env.id, vault_ids=[vault.id])
   ```

Anthropic auto-refreshes the OAuth tokens. Credentials never enter the
container — they're injected by an Anthropic-side proxy after the request
leaves the sandbox.

**For non-MCP secrets** (any other API token, CLI credential): there's
currently no way to set container env vars or expose vault credentials to
arbitrary processes. Use a **custom tool** instead — your orchestrator
holds the secret, agent emits a tool call, you make the authenticated call
with your credentials, return the result. Same pattern we use for
`deploy_site`.

## Resources — files and repos mounted at session start

```python
sessions.create(
    agent=agent.id,
    environment_id=env.id,
    resources=[
        # File from the Files API
        {"type": "file", "file_id": uploaded.id, "mount_path": "/workspace/data.csv"},
        # GitHub repository (clone-on-start)
        {"type": "github_repository",
         "url": "https://github.com/owner/repo",
         "authorization_token": os.environ["GITHUB_TOKEN"],
         "mount_path": "/workspace/repo",
         "checkout": {"type": "branch", "name": "main"}},
    ],
)
```

Files mount read-only; agent writes go to new paths. Max 999 file resources.

**Output retrieval:** files the agent writes to `/mnt/session/outputs/`
during the session can be listed and downloaded via the Files API:

```python
files = client.beta.files.list(
    scope_id=session.id,
    betas=["managed-agents-2026-04-01"],   # explicit on this endpoint
)
```

There's a 1–3s indexing lag after `session.status_idle`. Retry once or
twice if the list is empty.

## How we built this project — the implementation patterns

### `scripts/setup.py` — one-time agent + env creation

Every new agent type gets its own setup script. Pattern:

1. Build the system prompt (with any embedded values like a PostHog key
   substituted from env)
2. Define custom tool input schemas
3. Call `environments.create()` and `agents.create()`
4. Persist IDs to `setup.json` so `run.py` reuses them

Re-run setup whenever:
- System prompt changes
- Custom tool schema changes
- Model changes
- You want to bump to a fresh version

(Each `agents.create()` creates a new agent. For production iteration on
the same agent, use `agents.update(agent_id, ...)` — that bumps version on
the existing agent object instead of creating an orphan.)

### `src/run.py` — per-request runtime

Pattern in 6 steps:

1. Load `agent_id` / `environment_id` from `setup.json`
2. Create a session
3. Open the SSE stream (stream-first!)
4. Send the kickoff event (`user.define_outcome` for graded tasks, or
   `user.message` for simple chat-style)
5. Loop over events:
   - Handle text (print / stream to UI)
   - Handle `agent.custom_tool_use` → run host-side, post back result
   - Skip events with `session_thread_id` set (grader internal)
   - Break on terminal idle / terminate / error
6. Return the captured output

### `src/deploy.py` / `deploy_vercel.py` — custom tool handler

Returns `{url, site_id, name}`. Lives entirely host-side. The Netlify and
Vercel handlers have the same signature — `run.py` selects via env var:

```python
DEPLOY_BACKEND = os.environ.get("DEPLOY_BACKEND", "netlify")
```

**Liveness probe MUST NOT raise.** Early version of `deploy.py` raised on
liveness timeout, which made the agent see "deploy failed" and retry with
a different title. We burned through 15+ deploys in one outcome iteration
that way and triggered Netlify's free-tier burst block. The fix: do the
liveness probe but soft-return on timeout. Let the grader fetch the URL
itself and judge.

### `src/analytics.py` — orchestrator-side PostHog

Process-level events. Fails silently — analytics outages must never break
the build:

```python
def capture(event, distinct_id, properties=None):
    try:
        requests.post(f"{HOST}/capture/", json={...}, timeout=5)
    except Exception:
        pass  # never crash the build
```

We capture: `agent_run_started`, `agent_iteration_deployed`,
`agent_iteration_deploy_failed`, `agent_run_completed`, `agent_run_failed`.

A `run_id` (`run_<hex>`) ties all events for a single run together. Pair
with the page-side events to get end-to-end funnel from "agent starts
generating" → "page loaded" → "CTA clicked".

## Building a NEW agent for a different task

Step-by-step, reusing this project's bones:

### 1. Decide the task shape

| Task pattern | Example |
|---|---|
| **Generate-then-evaluate** | Landing pages, slide decks, reports — anything with a clear quality bar. Use **defined outcomes**. |
| **Chat / open-ended** | Q&A, customer support, agentic coding. Use plain `user.message` events, no rubric. |
| **One-shot** | Single tool invocation, no iteration. Don't bother with MA — just use the regular Messages API. |

### 2. Write the rubric (if generate-then-evaluate)

Live in `src/rubric.md`. Keep criteria binary. Group by category. Tie
hard requirements to mechanics the grader can verify.

For non-graded tasks: skip the rubric, send `user.message` instead of
`user.define_outcome`.

### 3. Define your custom tools

What does the agent need to *do* in your environment? A custom tool for
each external action it should be able to take — deploy, send email, post
to Slack, query DB, run tests, open a PR.

Schema in `scripts/setup.py`:

```python
SOME_TOOL = {
    "type": "custom",
    "name": "your_tool_name",
    "description": "Crisp one-liner describing what this does.",
    "input_schema": {
        "type": "object",
        "properties": {
            "param1": {"type": "string", "description": "..."},
        },
        "required": ["param1"],
    },
}
```

Then implement the host-side handler — see `src/deploy.py` for the shape.

### 4. Write the system prompt

Live in `scripts/setup.py`. Pattern:

- **Role** — one-line "you are X"
- **Process** — numbered steps the agent should follow
- **Hard requirements** — anything the grader will fail you for, listed
  verbatim. Often paste-able from the rubric.
- **Available tools** — describe when to use each (in addition to the
  schema descriptions)
- **Termination signal** — what counts as done

Keep it under a few thousand tokens. Front-load the most important rules.

### 5. Re-run `scripts/setup.py`

Creates a fresh agent + environment. New IDs land in `setup.json`. Old
agent stays around (orphaned but harmless) — clean up via
`agents.archive()` only if you're sure nothing depends on it. **Archive
is permanent. There is no unarchive.**

### 6. Run

`python main.py "<input>"`. Watch the logs in `/tmp/landing-run.log` (or
wherever you redirect stdout).

## Lessons learned — gotchas, in priority order

### 1. Liveness probes for external services must be soft-fail
If your custom tool fails on a liveness timeout, the agent treats it as a
real failure and retries. With outcome iterations, this can cascade into
many tool calls per outcome iteration. We burned a Netlify free-tier
quota this way. Always soft-return; let the grader judge.

### 2. The grader has its own session thread
Events from the grader carry `session_thread_id != None`. Don't try to
respond to its tool calls on the main session — it 400s. Skip them; the
grader resolves them internally.

### 3. SDK event field names
- `event.name` — tool name (not `event.tool_name`)
- `event.id` — the tool_use_id you echo back as `custom_tool_use_id` (not
  `event.tool_use_id`)
- `event.input` — already-parsed dict

### 4. `session.status_idle` is not terminal
Always check `stop_reason.type` before breaking. `requires_action` means
"waiting for you", not "done".

### 5. Stream-first ordering
Open the SSE stream before sending the kickoff event. Otherwise you miss
early events.

### 6. Beta headers
SDK auto-adds the standard MA beta. Don't override with research-preview
variants — they 404.

### 7. Don't call `agents.create()` per request
Setup is its own script. The runtime loads pre-existing IDs. Anything
else is wrong shape.

### 8. SDK type access patterns
`event.input` may be a dict or a Pydantic model — always defensive:
```python
inp = event.input
if not isinstance(inp, dict):
    inp = inp.model_dump() if hasattr(inp, "model_dump") else {}
```

### 9. Free-tier deployment quotas are real
Netlify's free tier has a burst block that hits at unclear thresholds and
locks the account for hours. The fix: have a fallback (we have
`deploy_vercel.py` ready). For production, use a paid tier or self-host.

### 10. PostHog key prefixes mean different things
- `phc_*` — Project API Key, client-side, can capture events. Safe to
  embed in HTML.
- `phx_*` — Personal API Key, server-side, manages PostHog itself. Can
  NOT capture events. Will return 401.

## Models cheat sheet (relevant for agent definition)

| Model ID | Use case |
|---|---|
| `claude-opus-4-7` | Default for high-quality agents. Adaptive thinking only (no `budget_tokens`, no `temperature`/`top_p`/`top_k`). |
| `claude-opus-4-6` | Previous-gen Opus, also adaptive thinking. |

(or `"max"` on Opus) for cost-quality control.

sub-agents on Sonnet or Haiku to save tokens. The coordinator stays on

## Multi-agent (future expansion — we don't use here)

If you ever need parallel sub-agents (e.g. one researcher + one writer +
one editor), the pattern is:

1. Create each sub-agent with its own `agents.create()` call. Capture IDs.
2. Create a **coordinator** agent with `multiagent.agents` listing the
   sub-agent IDs:
   ```python
   client.beta.agents.create(
       name="Coordinator",
       model="claude-opus-4-7",
       tools=[{"type": "agent_toolset_20260401"}],
       multiagent={
           "type": "coordinator",
           "agents": [
               {"type": "agent", "id": "$RESEARCHER_ID"},
               {"type": "agent", "id": "$WRITER_ID"},
               {"type": "self"},  # optional self-spawn
           ],
       },
   )
   ```
3. Sessions reference the coordinator. Sub-agent invocations happen via
   the coordinator's `agent_toolset_20260401` automatically.

**Caveats:**
- Depth > 1 is silently ignored (no nested coordinators).
- 25 concurrent thread cap per session.
- Sub-agent custom-tool events cross-post to the primary thread with
  `session_thread_id` — your handler must route by thread.
- 20 unique agents max in roster.

For most tasks, **a single agent with a strong system prompt beats a
multi-agent setup.** Only reach for sub-agents when you have genuinely
parallel, independent work (e.g. fan out 3 section-writers and merge).
